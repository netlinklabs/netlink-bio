# Changelog

All notable changes to Netlink.bio are documented in this file.

## [Unreleased]

### Added
- `api/moonpay-sign-url.js` — new serverless function that generates a signed, IP-matched MoonPay widget URL server-side, following the same style as `api/lifi-quote.js` (env var for the secret key, input validation, clean error responses, no Supabase calls). Reads `MOONPAY_SECRET_KEY` from `process.env` (500 if missing), validates `walletAddress` (`/^0x[a-fA-F0-9]{40}$/`) and `baseCurrencyAmount` (positive number) query params, and captures the client's IP from `True-Client-IP` → `X-Forwarded-For` (first entry) → `req.socket.remoteAddress`, in that order. Canonicalizes the IP per MoonPay's [IP matching](https://dev.moonpay.com/widget/on-ramp/customization/ip-matching) rules (strips port/brackets, unmaps IPv4-mapped IPv6, no leading zeros on IPv4 octets, lowercases IPv6), HMAC-SHA256-hashes it with the secret key (base64) as `allowedIpAddress`, builds the `buy.moonpay.com` widget URL, and HMAC-SHA256-signs the full query string (base64) as `&signature=`. Returns `{ signedUrl }`; the whole handler is wrapped in try/catch and never returns the secret key or a raw error stack. Not yet wired into `pay3.html` — `pay3.html`'s `startMoonPayWidget()` still uses `PLACEHOLDER_MOONPAY_PUBLISHABLE_KEY` and an unsigned client-side `init()` call.
- `pay3.html` — new experimental test page, an exact copy of `pay2.html` with the TransFi Payin widget replaced by a MoonPay On-Ramp widget (sandbox mode, placeholder publishable key). Loads the MoonPay Web SDK (`static.moonpay.com/web-sdk/v1/moonpay-web-sdk.min.js`) and, on clicking "Continue" in the new `startMoonPayWidget()` handler, opens `window.MoonPayWebSdk.init({...}).show()` as an overlay with `flow: 'buy'`, `environment: 'sandbox'`, `defaultCurrencyCode: 'usdc_polygon'`, and the existing `currentWalletAddress`. All TransFi-specific markup, functions (`startTransfiPayin`, `startTransfiStatusPolling`/`stopTransfiStatusPolling`, `showTransfiSuccessState`, `resetTransfiWidget`, `hideTransfiLoadingOverlay`, `collectPersonalDetails`, `updateRampIframe`), and API calls (`/api/transfi-create-order`, `/api/transfi-order-status`) were removed from this file only — `pay.html`, `pay2.html`, and the TransFi API routes are untouched. `loadDeletionGuardStatus()` was adapted to reference the renamed `moonpaySetup` element instead of `transfiSetup` (MoonPay's overlay has no iframe state to manage, so the `rampFrameWrap` handling was dropped in this file). Test page only — not linked from the main navigation.

Since `profiles_bio_public` already nulls out `country_code` when `show_country_bio` is false, no extra privacy check is needed here. `api/cv.js`'s JSON-LD `address` was corrected to use `addressLocality: city` and `addressCountry: profile.country_code` as separate structured fields instead of the previous single `addressLocality: location`, which had been reusing the human-readable `"City, 🇽🇽 Country"` display string (comma-joined and emoji-prefixed — wrong for structured data). The visual `location` variable and `.profile-location` display are unchanged — this only affects the JSON-LD block. `identity.html` also gained a small note under "Show Country on Bio Page" ("your CV always shows your country regardless of this setting") clarifying that the toggle only affects Bio, since the CV's country is unconditional.
- **CV City/Country split, sourced from the profile's Bio country** — CV's "Location" field is now "City" (`dashboard.html`'s `cvLocation` input; same ID and `cv_data.location` key as before, no data migration needed, just relabeled with a plain city placeholder). (The JSON-LD `address` was later split into separate `addressLocality`/`addressCountry` fields — see below.)

Since `show_country_bio` is also editable from `identity.html`'s "Show Country on Bio Page" toggle, it follows the exact same dirty-flag pattern already used for `show_donate`/Show Wallet on both sides: a `showCountryDirty` flag (per page) set only when the user actually touches the checkbox/toggle, reset to `false` on load and after a successful save, and only included in the `.update()` payload when dirty — so an untouched, possibly-stale value loaded on one page can never silently overwrite a change made on the other. `dashboard.html`'s `saveLinkCardSettings()` and `identity.html`'s `savePrivacySettings()` both gained the conditional block; `identity.html` no longer sends `show_country_bio` unconditionally.

Auto-generated on profile creation via DB trigger (`generate_net_id()`); existing users backfilled. Currently identity-only — no transactional use yet.

Shown in `renderMethods()` only when `hasGoogle` is false. ### Fixed
- `app-lock.js` and `privacy.html` — the `requireAppLock()` PIN/biometric modal (used before account-deletion request/cancel) had no way to back out except "Log out", which force-signed the user out of the session just to abandon the action. `renderVerifyScreen()` now accepts `allowCancel`/`onCancel` options; when set, a "Cancel" link renders next to "Log out" (`.nlal-links-row`). `requireAppLock()` now passes `allowCancel: true` and resolves the returned promise with `false` on cancel (previously only ever resolved `true`, on success). `privacy.html`'s `confirmDeletionRequest()` now also calls `closeDeletionModal()` when `unlocked` is `false`, so cancelling the PIN step closes the underlying "Request account deletion?" confirmation modal too, returning the user cleanly to the settings page instead of leaving a stray modal open behind the dismissed PIN screen. `cancelDeletion()` needed no change — it has no confirmation modal beneath it. The passive lock screen (`showPassiveLock()`/`checkAndShowLock()`) is unaffected — `allowCancel` defaults to `false` there, so "Cancel" only appears at explicit `requireAppLock()` call sites.
- `api/moonpay-sign-url.js` — fixed "Signature check failed" on the MoonPay widget: the signature was being computed over the bare query string (`apiKey=...&...`), but MoonPay's documented signing method (`crypto.createHmac('sha256', secretKey).update(new URL(url).search).digest('base64')`) signs `URL.prototype.search`, which includes the **leading `?`**. MoonPay's server reconstructs and compares against that `?`-prefixed string, so the old signature never matched. Now builds a real `URL` object from the widget URL and signs `widgetUrl.search` directly (rather than manually prepending `?`, to guarantee byte-for-byte parity with what MoonPay itself computes) — verified locally that the resulting signature validates against an independent HMAC recomputed the same way a verifier would. Query param order/names (`apiKey`, `currencyCode`, `baseCurrencyCode`, `baseCurrencyAmount`, `walletAddress`, `allowedIpAddress`, then `signature` appended after) were already correct and are unchanged. Also double-checked `pay3.html`'s `apiKey` (`pk_test_1RIFYNJJyP1IuDXDd8aLMKVcqodCof`) flows straight through to the final `signedUrl` with no separate/hardcoded key on the backend side — no mismatch found there. Added temporary `console.log` lines (canonicalized IP, `allowedIpAddress`, the exact signed string, and the final `signedUrl`) to `[moonpay-sign-url]`-prefixed lines in Vercel's function logs, to be removed once the fix is confirmed live — nothing secret is logged (no `MOONPAY_SECRET_KEY`, no raw client IP, and the two HMAC outputs are one-way).
- `dashboard.html` — the Show CV / Show Wallet / Show Country checkbox row in "Your Netlink.bio Link" was wrapping onto two lines on mobile once the third checkbox ("Show Country") was added. Tightened `gap-6`→`gap-4` and `text-sm`→`text-xs` on the row and its labels, added `flex-nowrap` on the container and `whitespace-nowrap` on each label so "Show CV"/"Show Wallet"/"Show Country" each stay on one line, and `shrink-0` on the checkboxes so they don't get squeezed. IDs, `onchange` handlers, and order are unchanged — only classes.
- **Country field UI/UX cleanup** (follow-up to the Country field feature above) — `dashboard.html`: moved the Country picker up to right after Display Name (was after Telegram, last in the list) and removed the redundant "Required before publishing..." helper paragraph underneath it, since the red `*` on the label already conveys that. `identity.html`: removed the "Your country: ..." read-only summary line above the "Show Country on Bio Page" toggle (and the `countryEntry` lookup that built it, plus the now-unused `country_code` column from the profile `select()` and the now-unused `shared/countries.js` `<script>` tag) so the toggle matches the plain look of the other Bio-group toggles. Also audited every save path in `dashboard.html` (`saveLinkCardSettings()`, `saveEditProfile()`, `saveDescription()`, `saveYoutube()`, `saveCv()` and its experience/education/projects/languages/certifications sub-sections, the individual link add/edit form, icon-shape/avatar/wallet saves) against what `api/bio.js` and `api/cv.js` actually read: `getCountryCodeOrBlock()` was already correctly wired into all three profile-save payloads (`saveLinkCardSettings()`, `saveEditProfile()`, `saveDescription()` each send `country_code`), and every other field validated/read from the DOM was confirmed to reach its `.update()`/`.insert()` payload and to be read back correctly by the public pages — no further validate-but-don't-send (or save-but-never-render) bugs found.
- `tx.html` — the amount in `rowHtml()`'s non-swap transaction card now goes through the existing `formatFintech()` helper instead of rendering `tx.amount` raw. A long unformatted decimal (e.g. a POL export amount like `0.7296392419257715`) widened the amount column enough to squeeze the title column, truncating the action label to something like "E..". Uses 2 decimal places (matching the receipt modal's amount display) except for POL, which uses 4 (matching the receipt modal's gas fee display) so small POL amounts don't round to "0.00". Display-only — `tx.amount` itself is unchanged in the database. Swap cards were not touched.
- `pay.html` — `finalizeWalletConnection()` now takes an `isGoogle` boolean and only writes `profiles.wallet_google_email` when the connection came from the Google credential flow (`onCreateWalletCredential`, passes `true`). The email OTP flow (`confirmEmailWalletConnect`, passes `false`) no longer writes to that column at all, since it previously mislabeled email-OTP addresses as Google-connected. Forward-only fix — no backfill of existing `profiles` rows. `pay2.html` has no email OTP wallet flow (Google-only, same as `dashboard.html`), so it wasn't affected and needed no change.
- **Financial safety** — `pay.html`, `pay2.html`, and `recovery.html` now verify the active Sequence WaaS session's wallet actually belongs to the logged-in Supabase profile before trusting it for a wallet-affecting action. `sequenceWaas` is a browser-global session that can outlive a Supabase login (a stale session from a previous account, or a different account signed in via another tab); previously only `isSignedIn()` was checked, so a mismatched session could silently drive Send (skip-relogin), Add Google/email backup, or Emergency Export against the wrong wallet while the UI showed the correct user's address/balance. Added a shared `sessionMatchesCurrentWallet()` helper (duplicated per page, matching this codebase's existing convention) that compares `sequenceWaas.getAddress()` against `currentWalletAddress`/`profiles.wallet_address` case-insensitively, and drops the session via `sequenceWaas.dropSession()` on mismatch so the next re-auth starts clean. Re-checked at every sensitive action, not just page load: `goToSendConfirm()` in `pay.html`/`pay2.html`; `ensureWalletSession()`, `renderMethods()`, `confirmRecoveryCode()`, `onGoogleBackupCredential()`, `openExportModal()`, and `doExecuteExport()` in `recovery.html`. `performTransfer()`, `doExecuteSend()`, and the `linkAccount()` calls themselves were not changed — only gated. **Needs careful manual testing before merge** (see PR for test plan) given the financial risk.

So instead of the overlay SDK call, the returned `signedUrl` is now loaded verbatim into a new iframe (`moonpayFrameWrap`/`moonpayFrame`) that replaces the amount-entry form in the widget card, with a loading overlay (`moonpayLoadingOverlay`) and a "Back" button (`resetMoonPayWidget()`) to return to the setup form — mirroring the loading-overlay convention the removed TransFi iframe used. The now-unused `static.moonpay.com/web-sdk/v1/moonpay-web-sdk.min.js` script tag was removed from `<head>` since the SDK is no longer called at all. `loadDeletionGuardStatus()` gained a third state (hiding `moonpayFrameWrap` when deletion is pending) to match. `api/moonpay-sign-url.js` itself, `pay.html`, and all other files are untouched.
- `shared/site-nav.js` — the header's "Get Started Free" CTA now points to `app.html` (temporary, until the app is live) instead of `login.html`. The "Login" nav links are unchanged.
- `pay.html` — USDC card ID display now reads the real `net_id` from Supabase instead of generating a random value on every page load.
- `pay.html` and `pay2.html` — `goToSendConfirm()` now checks `sequenceWaas.isSignedIn()` before showing the send confirmation step. If the Sequence WaaS session is already active, it skips the Google/email-OTP re-auth prompt and shows a direct "Confirm Send" button (built with `document.createElement` + `addEventListener`, not an inline `onclick`) that calls `doExecuteSend()`; if the session is not signed in, the existing Google sign-in confirm flow (with email OTP fallback on `pay.html`) is unchanged. Promoted from the `pay3.html` experiment, which has been removed now that its logic lives in production. `performTransfer()`, `doExecuteSend()`, and the wallet connect/disconnect flow were not touched.
- `pay.html` and `pay2.html` — the "No wallet yet" toast shown when opening Send or Receive without a connected wallet now reads "No wallet connected — tap Connect Wallet to continue", matching the wording already used elsewhere (`copyWalletAddress()`, the swap error state). Text-only change; no logic touched.
- `recovery.html` — the intro card ("Add a backup sign-in method" / "Your wallet currently only opens with Google...") is now hidden once `renderMethods()` detects a linked email account, same as `addEmailCard` is hidden and `alreadyLinkedCard` is shown in that case. Previously this text stayed visible even after the user had already linked email, contradicting the methods list below it. Gave the card `id="introCard"` so it can be targeted.

### Removed
- **TransFi integration** — `api/transfi-create-order.js`, `api/transfi-order-status.js`, and `api/transfi-webhook.js` (disabled webhook, tracked as `api/transfi-webhook.js.`) were deleted. TransFi's setup fee isn't viable for the current budget, so this integration is no longer being pursued. `pay2.html` (the TransFi test page) was removed along with it since it depended entirely on these routes and has no purpose without them. `pay.html` (production, Alchemy Pay) and `pay3.html` (the MoonPay sandbox experiment, see Added above) are unaffected. This also fixes deployment: Vercel's Hobby plan caps a project at 12 serverless functions, and removing these 3 TransFi routes was needed to free up a slot for `api/moonpay-sign-url.js` — the project was blocked at 13 functions before this change. Note: `CLAUDE.md`, `README.md`, and a couple of comments in `recovery.html` still reference `pay2.html`/TransFi by name (e.g. `recordTransaction()`'s "same pattern as pay.html/pay2.html" comments, `CLAUDE.md`'s wallet-security file list, `README.md`'s directory tree) — left as-is since updating them wasn't part of this change; worth a follow-up pass.
- `pay3.html` — experimental page for the skip-relogin Send flow. Its logic has been merged into `pay.html` and `pay2.html`; the standalone experiment is no longer needed.
