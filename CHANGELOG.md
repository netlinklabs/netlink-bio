### Added
- **New `pay5.html`, `shared/netlink-trails.js`, and `api/trails-config.js` — isolated card on-ramp experiment via Sequence's Trails SDK** (Meld/Topper/Banxa/Stripe card providers), built as an exact clone of `pay.html` with the "Buy Crypto" section wired to Trails instead of the disabled Onramp.Money widget. Not linked from any nav/menu — reachable only by typing the URL directly, same convention as `pay2.html`.
  - **`shared/netlink-trails.js`** is a self-hosted esbuild bundle of `0xtrails@0.18.6` (React 19 + `0xtrails/widget`'s `Fund` component), built because Trails' official CDN builds are unusable: `dist/umd` is stuck serving `0.16.2` (predates the card on-ramp entirely) and `dist/iife` (0.17+) throws `X is not a function` on load in every version tested (0.17.0–0.18.6, verified via a Node/jsdom harness). Exposes `window.NetlinkTrails.renderFund(container, props)`, returning `{ open, close, hasModal, unmount }` — `pay5.html` calls `.open()` after a short mount delay instead of relying on the (nonfunctional, in this bundle) auto-render-on-click pattern from the docs.
  - **`api/trails-config.js`** serves the Trails client key from a new `TRAILS_API_KEY` Vercel env var (`GET`-only, `Cache-Control: no-store`) instead of hardcoding it in `pay5.html`, so it can be rotated without an HTML edit. The key is still client-visible by design (the widget runs in-browser) — the actual protection is restricting it to `netlink.bio` in the Trails/Sequence dashboard, if that option exists there.
  - **`pay5.html`'s "Buy with card" button** renders Trails' `Fund` component with `paymentMethod: 'CREDIT_DEBIT_CARD'`, `to: { recipient: <user's wallet>, chain: 'polygon' }`, and a `hostWallet` prop carrying a hand-built **read-only** EIP-1193 provider (reports the Netlink Pay wallet address + chain 137; rejects every other RPC method, including all signing/sending) — this is Trails' documented "host-owned wallet" adapter pattern (used for apps like thirdweb/Privy/Fireblocks with their own embedded wallet), which lets the widget skip its "Connect Wallet" screen entirely for a wallet with no EIP-1193 provider of its own, while guaranteeing the read-only shim can never move funds. `hideSwap: true` (Swap needs a real signature this wallet won't provide) and a `customCss` override (`.trails-modal-frame{max-height:96dvh;overflow-y:auto}`) so Trails' own non-scrollable centered modal doesn't clip its longer screens (provider list + fee breakdown) on a phone viewport.
  - **A diagnostic line under the button** (`checkTrailsAvailability()`) calls the same `GetOnrampProviderAvailability` endpoint the widget itself uses, for a given country code, and prints which of Meld/Stripe/Mesh/Bluvo are enabled — used during testing to confirm Meld is available for Indonesia (`ID`) independent of any card/bank-level failure.
  - **Result of live testing (2 different card issuers, 4 attempts total, no funds ever lost — every attempt shows `Declined`)**: the integration works end-to-end — widget loads, provider checkout (Topper, Banxa) opens, identity verification completes, card is charged. **Both a BCA debit Mastercard and a Rizon virtual Visa were declined** at the issuer, not by Trails/Topper/Banxa/Netlink. Rizon's own transaction history shows the explicit reason: `"Jenis merchant tidak diizinkan"` (merchant category not permitted) — a crypto-purchase MCC block at the card-issuer level, consistent with a same-card top-up to Sequence's own (non-crypto-MCC) Stripe billing succeeding on the very same BCA card minutes earlier.
  - **Decision: card on-ramp shelved as a path for Indonesian users** — the blocker is issuer-side MCC policy, which this integration (or any on-ramp integration) can't work around, and Trails' widget only exposes 6 fixed funding methods (card, exchange, PayPal, Google Pay, Apple Pay, SEPA) with no way to surface Meld's local Indonesian rails (QRIS, VA) even though Meld itself may support them elsewhere. `robots.txt` not yet updated to `Disallow: /pay5$` (follow-up). Continuing with Guardarian/Onramp.Money/Transak (QRIS/VA/bank-transfer rails) as the primary on-ramp path for Indonesian users; Trails/`pay5.html` may still be worth revisiting for international cardholders in Stripe's supported region (US + 27 EU states) or where card-issuer MCC blocks don't apply.

### Fixed
- **`privacy.html`: the consent modal (`#consentModal`) and "Request account deletion?" modal (`#deletionModal`) no longer show on page load.** Root cause: the page's inline `<style>` defined `.modal-overlay { ...; display: flex; ... }` with no gating class, relying on Tailwind's `.hidden` to hide it. Both selectors are single-class (equal specificity), and the inline `<style>` loads after `<link href="/shared/tailwind.css">`, so `.modal-overlay{display:flex}` won the cascade over `.hidden{display:none}` and both modals (`class="modal-overlay hidden"`) were always visible. Fix (CSS only, JS untouched — it still toggles `hidden`): `.modal-overlay` now defaults to `display: none`, and a new `.modal-overlay:not(.hidden) { display: flex; }` rule shows it — same default-hidden pattern used in `contacts.html`/`pay.html`/`pay2.html`/`pay5.html` (which gate on `.active`). No new Tailwind classes, so no `npm run build:css` rebuild needed.
- **Swap (POL ↔ USDC via LI.FI) on `pay.html`/`pay2.html` no longer fails with "endpoint error" on wallets that are near-0 POL and not gas-sponsored.** Root cause: `executeSwapTx()` picked a fee option with `feeOptions.find(q => symbol === 'POL' || 'MATIC') || feeOptions[0]` — no balance check at all, so a wallet with e.g. 0.0023 POL still got quoted a POL fee option it couldn't actually pay, and the relayer rejected the transaction. Scope: swap only, changed only inside the swap `<script type="module">` block (`SWAP_TOKENS` through the bottom of the file) in both `pay.html` and `pay2.html`, identically. Send's `performTransfer()`, `onSendTokenChange()`, `checkGasSponsorship()`, `openSendModal()`, `#sendContinueBtn`, `#gasWarning`, the Send modal, and `window.isGasSponsored` are untouched — verified with a post-change diff grep for every one of those names, only comment mentions remain, no call sites or logic changed.
  - **`executeSwapTx()`** now logs the raw `feeOptions` response (`console.log(feeOptions)`) for diagnosing future relayer responses, and picks a fee option via a new `pickSwapFeeOption()` helper: POL/MATIC first, then USDC, each checked against `window.currentBalances` (converted to the option's smallest unit and compared as `BigInt`) — the first one the wallet can actually afford wins. If neither is affordable, it now throws `"Not enough balance to cover gas fees. Top up POL or use a sponsored wallet."` instead of silently sending a doomed transaction. (The task that requested this fix specified the error text in Indonesian; translated to English per this repo's "UI text, error messages, and user-facing strings: English only" rule in `CLAUDE.md`, which applies even when the requester writes in Indonesian.)
  - **Approve + swap are now batched into one `sendTransaction` call** (`transactions: [approveTx?, swapTx]`, 1 or 2 items) instead of two separate `executeSwapTx()` calls — `feeOptions()` is queried once against that same batch so the returned `feeQuote` matches exactly what gets sent, instead of two independent quotes that could drift between the approve and the swap.
  - **USDC-fee swaps are capped so enough USDC is left to cover the fee**: a new `getMaxUsdcSwapAmount()` (used from `onSwapAmountInput()`) reserves the last-known fee estimate (+10% buffer) off the USDC balance when `swapFrom === 'USDC'` and the fee is expected to come out of USDC, and blocks the quote with an inline warning ("Reserve some USDC for gas — max swappable right now is X USDC.") if the entered amount would eat into that reserve.
  - **New swap-only sponsorship check, `checkSwapGasStatus()`**, mirrors the shape of Send's `checkGasSponsorship()` (session-match guard via `sequenceWaas.getAddress()`, then a representative `feeOptions()` call) but is entirely separate: its result lives in a new module-local `swapGasSponsored` variable (plus `swapFeeTokenSymbol`/`swapEstimatedFeeAmountWei`), never `window.isGasSponsored`. Runs on every `renderSwapTokens()` (wallet connect, balance refresh, token flip) and again when the swap confirm modal opens, so it stays fresh the same way Send's check does on its own triggers.
  - **New banner, `#swapGasBanner`** (separate id from `#gasWarning`), shown above the swap card's "You Pay" field: green ("Gas-free swap — network fees are covered by Netlink.") when `checkSwapGasStatus()` confirms sponsorship, yellow ("Gas fee for this swap is deducted from POL/USDC.") when it isn't. Reuses the existing `.gas-warning`/`.gas-warning-sponsored` CSS classes (already defined for Send's banner) for visual consistency — no new CSS needed, and `hidden`/`mb-3` are pre-existing Tailwind utility classes already used elsewhere on these pages, so no `npm run build:css` rebuild was required for this change.
