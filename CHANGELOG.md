## [Unreleased]

### Added
- **Bio page 404 log, to tell bots from mistyped links.** Every time `api/bio.js` answers 404 (username does not exist) it now records the username in a new table, counted per day. No new serverless function (the `api/` folder stays at 12).
  - `supabase/migrations/20261006_bio_not_found_log.sql`: table `bio_not_found_daily (day, username, count)` and function `bump_bio_not_found(p_username)`. RLS on, no policies, only `service_role` can read, write or execute. Max 300 distinct usernames per day (extras are counted as `(other)`), rows older than 30 days are removed automatically. Migration is NOT applied yet.
  - `api/_lib/stats.js`: new `logBioNotFound(username)`, fire and forget through `waitUntil`, never throws.
  - `api/bio.js`: calls `logBioNotFound(username)` in the 404 branch only (not for the 400 missing username case).
  - Read it in the Supabase SQL editor: `select username, sum(count) n from bio_not_found_daily where day >= current_date - 7 group by 1 order by n desc limit 30;`

Manual check: call the cron URL with `?job=process-deletions` (same `Authorization: Bearer $CRON_SECRET`). The result is also in the normal cron response as `accountDeletions`.

### Security
- **Fixed script injection through link icons, and hardened links and colours on public pages (`api/bio.js`, `api/landing.js`, helpers `safeHttpUrl` and `safeCssColor` in `api/_lib/html.js`, migration `supabase/migrations/20261006_links_validate_icon_url.sql`, applied to production 2026-10-06).**
  - **Icon (real, zero click):** `iconHtml()` in `bio.js` wrote `links.icon` unescaped into an image `src`. A value like `x" onerror="...` ran script as soon as the public bio page opened, for every visitor. It needs no click. Tested in headless Chromium: old code ran the script, new code does not. Icon names are now limited to `^[a-z0-9-]{1,40}$`, anything else shows the default link emoji.
  - **Link and video URLs:** `bio.js` now only writes `http(s)` URLs into `href` (otherwise `#`). Tested: a `javascript:` link did not run in the page origin anyway, because links open with `target="_blank" rel="noopener"`, so this is defense in depth.
  - **Landing page:** the brand colour must be a hex, `rgb()` or `hsl()` value (otherwise the default), so extra CSS cannot be added inside `style=""`. The map link must be `http(s)`.
  - **Database (applied 2026-10-06, verified):** check constraints `links_icon_format`, `links_url_http`, `profile_videos_url_http`. Production data checked first: 0 rows violate them. Bad icons and non-http(s) URLs are now rejected at write time, including direct API writes. The render-side checks above stay as a second layer.
  - Still open: the `onclick="trackClick(...)"` attribute in `bio.js` (value is the link id, attribute context), and `lucide-static@latest` / `simple-icons@latest` loaded from jsDelivr without a pinned version.
- **Fixed script injection through inline JSON in public pages (`api/bio.js`, `api/cv.js`, `api/landing.js`, new helper `jsonForScript` in `api/_lib/html.js`).** The JSON-LD block and the inline JS values (display name, share data, wallet address, slug, gallery images, CV base path) were written with plain `JSON.stringify`, which leaves `</script>` intact. Tested in headless Chromium with a malicious display name, summary and certificate name: old code ran the injected script and broke the JSON-LD, new code does neither. Not changed: the `onclick="trackClick(...)"` attribute in `bio.js` (attribute context, different fix) and the `escapeHtml` output, which was already safe. Follow-up to check: whether the dashboard or the database already limit these fields (this fix does not depend on it).

### Added
- **CV certificate PDFs: watermark and "unverified" note (`api/cv.js`, new dependency `pdf-lib`).**
  - Every page of a certificate PDF is stamped on the server with a light diagonal text: `netlink.bio/cv/<username> | shown <date, UTC> | unverified copy`. The stamp is inside the served file, so it also appears in downloads, "Open in new tab" and screenshots. It does not stop a determined forger (it can be cropped or edited), but a copy visibly says where it came from.
  - The popup shows a small note: "Unverified document, uploaded by the profile owner. Not checked by Netlink." The "Verified Profile (KYC)" badge only verifies identity, not certificates, so the note avoids that confusion.
  - A file that cannot be stamped (corrupt, more than 30 pages) is not shown: the route answers 422 "This certificate file could not be displayed." and never serves the unstamped original. The original file in storage is not changed.
  - Tested with a 2 page PDF (stamp covers the page, text stays readable, popup renders it on canvas) and a corrupt PDF (422). Not tested yet: very large or encrypted real world certificates, please try a few real files after deploy.
  - Side effects: a few ms of CPU per certificate view, and `package.json` / `package-lock.json` gain `pdf-lib`.
- **CV JSON-LD: certificate names as `hasCredential` (`api/cv.js`).** Each certification title is listed as an `EducationalOccupationalCredential` (name only). The PDF is private and `noindex`, so no file link is exposed. Profiles without certifications emit no `hasCredential`.
- **Public pages: changelog and plans updated for the CV change.** `changelog.html` has a new October 2026 entry (certificate files, project links, print margins). `plans.html` renames the CV line to "Basic Professional CV" on the Basic card and "Advance Professional CV" on the Silver and Gold cards.
