# Changelog

All notable changes to Netlink.bio are documented in this file.

## [Unreleased]

### Fixed
- **`pay.html`'s Onramp.Money widget skipped straight to buying USDC, so its "Pilih Koin" (choose coin) screen — which also offers POL — never showed.** The `new OnrampWebSDK({...})` config hardcoded `coinCode: 'USDC'`, forcing that coin selection up front. Removed that line so the widget lets the user pick between POL and USDC themselves. `network: 'matic20'` is unchanged.
- **`shared/nav.js` and `pay.html` — the Onramp.Money widget didn't re-theme when the user toggled Dark/Light/System from the Account sheet**, because `applyTheme(theme, save)` only flipped the `html.dark`/`html.light` class and had no way to notify other pages that needed to react. `applyTheme()` now also dispatches `window.dispatchEvent(new CustomEvent('netlink-theme-changed', { detail: { dark: resolved === 'dark' } }))` right after the class toggle. `pay.html` listens for it (near `initTheme()`) and calls `updateOnrampWidget(currentWalletAddress)` when it fires (only if a wallet is connected), so the widget re-inits with the correct theme immediately instead of requiring a page reload.
- **`pay.html`'s `updateOnrampWidget()` was passing an invalid network code to the Onramp.Money Web SDK**, causing it to reject USDC purchases with "Jaringan yang dipilih (POLYGON) tidak didukung untuk transaksi USDC". The `new OnrampWebSDK({...})` config used `network: 'polygon'`, but Onramp.Money's `chainSymbolMapping` expects `'matic20'` for Polygon (alongside `erc20`, `bep20`, `trc20`, `spl`, `bep2`) — `'polygon'` isn't one of their recognized codes. Changed only that one `network:` value inside the `OnrampWebSDK` config; the unrelated `network: 'polygon'` params used by Sequence WaaS (`sequenceWaas.feeOptions`/`sequenceWaas.sendTransaction`, for both the send flow and the LI.FI swap flow) are a different SDK's parameter and are untouched.

### Changed
- **`pay.html`'s "Buy Crypto" ramp migrated from Alchemy Pay to the Onramp.Money Web SDK (embedded mode)** — the `<iframe id="alchemyRampFrame">` (pointed at `ramp.alchemypay.org`) is replaced with a plain `<div id="onrampWidgetContainer">` that the SDK renders into. Since `@onramp.money/onramp-web-sdk` ships ESM-only (no UMD build), it's loaded via a `<script type="module">` that imports it from jsDelivr's `+esm` endpoint and exposes it as `window.OnrampWebSDK`, dispatching a custom `onramp-sdk-ready` event the main inline script listens for (`onrampSdkReady` flag) since module scripts execute asynchronously relative to the classic script below them. `updateRampIframe(address)` (URL-param-based iframe navigation) is replaced with `updateOnrampWidget(address)`, which closes any existing SDK instance before constructing a new `OnrampWebSDK({ appId: ONRAMP_APP_ID, walletAddress, coinCode: 'USDC', network: 'polygon', containerId: '#onrampWidgetContainer', theme })` and calling `.show()` — same early-return guards as before (`window.hasPendingDeletion`), plus a new one for `onrampSdkReady` (module script hasn't finished loading yet; the `onramp-sdk-ready` listener retries once it fires). `theme` now follows the page's active Light/Dark mode via `theme.default` (`lightMode`/`darkMode`) instead of the old `theme=light|dark` URL param. Also wires `onrampSDK.on('TX_EVENTS', ...)`: on `ONRAMP_WIDGET_TX_COMPLETED` it shows a "Purchase completed! Your balance will update shortly." toast and re-fetches wallet balances after an 8s delay (giving the on-chain transfer time to land before the balance poll). All 3 call sites (`loadUserProfile()`, `initTheme()`, `finalizeWalletConnection()`) updated to call `updateOnrampWidget(...)`. Purely a ramp-provider swap — all "Powered by"/disclaimer copy and the FX-conversion comment now say "Onramp.Money" instead of "Alchemy Pay"; no other section of `pay.html` changed.

### Fixed
- **`shared/app-lock.js`'s `requireAppLock()` PIN screen rendered unstyled on pages that only call `setContext()`** — `requireAppLock()` never called `injectStyles()` itself; this went unnoticed because every page that calls `requireAppLock()` used to call `init()` first (which does inject the styles). `privacy.html` now calls `setContext()` instead of `init()` (it never needs the passive lock screen, only `requireAppLock()` for delete-account/cancel-deletion), so its `#nlal-styles` `<style>` tag was never injected — the PIN modal rendered as unstyled plain text stuck at the bottom of the page instead of a centered keypad modal. Added `injectStyles();` as the first line of `requireAppLock()`; it's a no-op if the styles are already present (`injectStyles()` already guards with `if (document.getElementById('nlal-styles')) return;`), so pages that already call `init()` are unaffected. Only `shared/app-lock.js` changed.

### Fixed
- **`shared/app-lock.js`'s PIN/biometric lock screen could render behind a page's own modal** — `#nlal-overlay` (the passive lock screen) and `#nlal-modal-overlay` (`requireAppLock()`'s modal) both used `z-index: 200`, the same value several pages use for their own modals (e.g. `privacy.html`'s `.modal-overlay`, including `#deletionModal`). If a page modal was already open when `requireAppLock()` fired — e.g. clicking "Confirm Deletion" inside `privacy.html`'s `#deletionModal` — stacking order between two elements at the same `z-index` came down to DOM order, so the PIN screen could end up rendered behind the page's modal and be unclickable. Raised both `#nlal-overlay` and `#nlal-modal-overlay` to `z-index: 9999` so App Lock's screen always renders above any page-level modal, regardless of render order. No other file changed.

### Fixed
- **`dashboard.html`'s "Complete Your Profile" checklist** — the "Upload Avatar" item auto-checked itself for users who signed in via Google, because `profiles.avatar_url` gets populated from the Google OAuth profile photo (a `googleusercontent.com` URL) at sign-in, not only from an actual upload to Netlink — so `avatar_url` alone couldn't tell "uploaded via Netlink" apart from "happened to come from OAuth". `hasAvatar` in `updateProfileCompletion()` now also checks that `avatar_url` contains `/storage/v1/object/public/avatars/`, the path `handleAvatarUpload()` always writes to (Supabase Storage `avatars` bucket), so only a real Netlink upload counts.
- **`dashboard.html`'s "Complete Your Profile" checklist** — `updateProfileCompletion()`'s `el.querySelector('i')` threw `TypeError: Cannot read properties of null (reading 'setAttribute')` in production once `lucide.createIcons()` had already run once on page load, since Lucide replaces each `<i data-lucide>` checklist icon with an `<svg>`, and `<i>` no longer matches on the next call. Changed the selector to `el.querySelector('[data-lucide]')`, which matches the `data-lucide` attribute regardless of whether Lucide has converted the element to `<svg>` yet.
- **`card.html`, `tx.html`** — `.toast` had `opacity: 0` (hidden) but no `pointer-events: none`, and its resting `translateY(100px)` offset placed the invisible element over the bottom nav, which sits at `z-index: 30` versus the toast's `z-index: 60`. The invisible toast was swallowing clicks on the centre nav tabs (Wallet, Activity) even when no toast was showing. Added `pointer-events: none` to the base `.toast` rule and `pointer-events: auto` to `.toast.show`, matching the pattern already used in `dashboard.html`, `pay.html`, and `contacts.html`.
- **`card.html`** — `shared/nav.js` and `shared/account-menu.js` were being loaded after the page's inline script, which calls `NetlinkNav.init()` (inside `loadProfile()`, awaited from `checkAuth()`). Depending on how quickly `supabaseClient.auth.getSession()` resolved relative to those two `<script src>` tags loading, `window.NetlinkNav` could still be `undefined` when `init()` ran, silently skipping it (guarded by `if (window.NetlinkNav)`) — the header/bottom-nav never rendered, so nothing on the page (Wallet, Activity, Dashboard, Account) was clickable. - **`api/wallet-balance.js` migrated from PolygonScan/Etherscan V2 to Alchemy RPC** — root cause of the wallet balance card failing was an invalid/misconfigured `POLYGONSCAN_API_KEY` in the Vercel Production env var (confirmed via temporary debug logging, since removed, that the key loaded at runtime kept mismatching what was set in the dashboard, and Etherscan's V2 API rejected it with "Invalid API Key"). Rather than keep chasing the PolygonScan key, this endpoint now calls Alchemy's Polygon Mainnet JSON-RPC directly via native `fetch` (no new library — `eth_getBalance` for POL, `eth_call` on `balanceOf(address)` with manual ABI encoding for NET/USDC), reading `ALCHEMY_API_KEY` instead. `fromWei()` is unchanged (it already parses `BigInt()`-compatible hex or decimal strings), and the response shape to the client (`{ pol, net, usdc }`) and `Cache-Control` header are unchanged, so `dashboard.html`/`pay.html` needed no changes. This is a partial migration — `api/tx-gas-fee.js` and `api/wallet-transactions.js` still use `POLYGONSCAN_API_KEY` and were intentionally left untouched.
- **`api/wallet-balance.js` now sends the 3 Alchemy RPC calls as a single JSON-RPC batch request** instead of 3 separate `Promise.all()` fetches, to reduce rate-limit pressure when navigating quickly between pages. `rpcCall()` was replaced with `rpcBatchCall()`, which POSTs an array of `{ jsonrpc, id, method, params }` request objects and returns Alchemy's array response as-is. Batch responses aren't guaranteed to preserve request order, so results are matched back to their request by `id` (not by array position) before checking each item's own `error` field individually. `fromWei()`, `balanceOfData()`, the response shape to the client, and the overall try/catch → 502 error handling are unchanged.
