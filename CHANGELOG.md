## [Unreleased]

### Security
- **Public views are now read with the service role key (step 1 of 3 for the Supabase "Security Definer View" warnings).** New `api/_lib/public-db.js` (`supabaseAuthHeaders`) picks the key per request: `profiles_bio_public`, `profiles_cv_public` and `landing_pages_public` use `SUPABASE_SERVICE_ROLE_KEY` (server env only, never sent to the browser); every other table keeps the public anon key. Used by `api/bio.js`, `api/cv.js`, `api/landing.js`, `api/og.js`, `api/track-event.js` and `api/_lib/sitemap.js`. No page output changes. Falls back to the anon key if the env var is missing (Preview deploys only have it for Production), so nothing breaks before step 2.
- **Public views hardened, applied to production 2026-10-04 (steps 2 of 3).** `profiles_bio_public`, `profiles_cv_public` and `landing_pages_public` are now `security_invoker = true`, and `anon`/`authenticated` have no access to them (also removed the stray `TRUNCATE`/`REFERENCES`/`TRIGGER` grants). `service_role` has `SELECT` on the views and on `landing_pages`. The 3 CRITICAL "Security Definer View" advisor errors are gone. Migration files: `20261004_public_views_service_role_select.sql`, `20261004_public_views_revoke_anon.sql`, `20261004_public_views_security_invoker.sql`.
- Incident note: right after PR #261 deployed, `/username` and `sitemap.xml` returned errors for 1 to 2 minutes because `service_role` had no `SELECT` on the views (fixed with a GRANT). After `security_invoker` was enabled, `/page/<slug>` failed for about 1 minute until `service_role` got `SELECT` on `landing_pages`. Lesson: grant first, then switch. All pages verified afterwards.
- **RLS performance: `auth.uid()` wrapped as `(select auth.uid())` in 33 policies across 19 tables, applied to production 2026-10-04.** Uses `ALTER POLICY`, so role, command and name are unchanged and the access rules are the same. Tables: admin_users, ambassador_applications, analytics_daily_summary, contacts, deletion_requests, fiat_orders, kyc_sessions, landing_pages, links, notification_reads, notifications, orders, profile_videos, profiles, referrals, rewards, user_consents, verifications, wallet_transactions. The "Auth RLS Initialization Plan" advisor warnings are gone. Migration file: `20261004_rls_wrap_auth_uid_in_select.sql`.
- **Dropped duplicate policy `Users manage own landing page` on `landing_pages`** (applied 2026-10-04 in the SQL Editor). The 4 per-command owner policies cover the same commands, so access is unchanged. Most "Multiple Permissive Policies" warnings on `landing_pages` are gone. Left as is: the 2 intentional admin+own policy pairs (`kyc_sessions`, `orders`), 8 unindexed foreign keys, 6 unused indexes.
- **Function `search_path` locked on 18 public functions, applied to production 2026-10-04.** `set search_path = public, pg_temp` (none use extension functions, so logic is unchanged). Includes the `SECURITY DEFINER` function `handle_new_user`. The "Function Search Path Mutable" advisor warnings are gone. Migration file: `20261004_functions_set_search_path.sql`.
- **`anon` can no longer execute 26 of the 28 `SECURITY DEFINER` functions, applied to production 2026-10-04.** 10 trigger functions (`handle_new_user`, `enforce_*`, `notify_*`, `check_*_reserved`, `sync_verification_cache`, `rls_auto_enable`) are revoked from everyone (triggers do not need EXECUTE). 16 signed-in-only functions (notifications, app PIN, consent, account deletion, `resolve_receipt_party`, `resolve_wallet_owner_name`) are revoked from `anon` and re-granted to `authenticated` and `service_role`. Kept public on purpose: `get_slug_status` and `is_slug_available` (username check on `index.html` before login). Advisor count for anon went 28 to 2. Migration: `supabase/migrations/20261004_revoke_anon_execute_security_definer.sql`.
- **Duplicate SELECT policies merged and public bucket listing closed, applied to production 2026-10-04.** `kyc_sessions`, `orders` and `landing_pages` now have one SELECT policy each (same access as before: owner or admin, or published page). Dropped the broad public SELECT policies on `storage.objects` for `avatars`, `banners` and `landing-images`, so nobody can list all files; public URLs still work. Added owner-scoped SELECT for `avatars` and `banners` because upload with `upsert: true` needs it (`landing-images` already has an owner ALL policy). Advisor warnings `multiple_permissive_policies` and `public_bucket_allows_listing` are gone. Migration: `supabase/migrations/20261004_merge_select_policies_and_storage_listing.sql`.
- **Dropped unused column `profiles.net_id_discoverable`, applied to production 2026-10-04.** Left over from the removed NET ID contact feature. Verified no code, view, function, policy or index referenced it. Migration: `supabase/migrations/20261004_profiles_drop_net_id_discoverable.sql`.
- **Dropped unused function `resolve_wallet_owner_name(text)`, applied to production 2026-10-04.** Old receipt helper replaced by `resolve_receipt_party` (still used by `tx.html`). It was not called anywhere and already broken (it read the removed column `profiles.show_name_on_receipt`). Migration: `supabase/migrations/20261004_drop_resolve_wallet_owner_name.sql`.
- Still open (optional): Auth "Leaked password protection" is off (not relevant for Google/OTP login).

### Removed
- **Contacts: "add contact via NET ID" removed.** `contacts.html` now only supports manual contacts (nickname + wallet address): add, edit nickname, reorder, delete. The Send modal contact picker in `pay.html`, `pay2.html` and `pay5.html` reads only `contacts.manual_address` and no longer queries `profiles_bio_public`. This also fixes the bug where a saved NET ID contact was missing from the Send modal when its owner had `show_donate` off (wallet came back NULL from the view).
- `tx.html`: removed the `contact_added` notification icon (type and CSS). `privacy.html`: removed the "Discoverable via NET ID" toggle and its read/write of `profiles.net_id_discoverable`. `faq.html` (visible answer and FAQPage JSON-LD) and `llms.txt`: NET ID is now described as the number on the Netlink Pay card, with payments sent to wallet addresses.
- Data migration `supabase/migrations/20261004_contacts_net_id_to_manual.sql` (applied to production 2026-10-04): the 8 NET ID contacts were converted to manual contacts (wallet and nickname copied from the profile, `contact_user_id` set to NULL). Verified: 0 NET ID contacts left, 21 of 21 contacts have a valid `0x` address.
- **Contacts cleanup applied to production 2026-10-04** (run in Supabase SQL Editor, verified afterwards): dropped trigger `trg_notify_contact_added`, functions `notify_contact_added()` and `resolve_net_id(text)`, the 7 `contact_added` notifications, index `contacts_owner_contact_unique`, constraints `contacts_exactly_one_target`, `contacts_manual_requires_nickname`, `contacts_no_self_reference`, `contacts_contact_user_id_fkey`, and column `contacts.contact_user_id`. `manual_address` and `nickname` are now `NOT NULL`, and new check `contacts_manual_address_format` requires a valid `0x` address. Migration files: `20261004_contacts_drop_net_id_trigger_and_functions.sql`, `20261004_contacts_drop_contact_user_id.sql`. Still open: `profiles.net_id_discoverable` is unused but not dropped.

### Added
- **Security: least privilege on `reserved_usernames`.** Migration `supabase/migrations/20261004_reserved_usernames_revoke_extra_grants.sql` (applied to production 2026-10-04) revokes `TRUNCATE`, `REFERENCES` and `TRIGGER` from `anon` and `authenticated`. Nothing used them. `SELECT` for `authenticated` is unchanged, rows stay at 274, and `get_slug_status` plus both reserved-name triggers (`profiles`, `landing_pages`) were re-checked and work as before. Closes the open note from the previous entry. `service_role` still holds those three grants (server-side only), left as is.
- **Server-side reserved names: 22 page names added.** `reserved_usernames` (enforced by triggers on `profiles.username` and `landing_pages.slug`, and by `get_slug_status` / `is_slug_available`) already existed in the database with 252 names but was not in the repo. Migration `supabase/migrations/20261004_reserve_page_names.sql` (applied to production 2026-10-04, 252 to 274 rows) adds the page names that were only in the browser list: 404, ambassador, analytics, business-page, changelog, checkout, contact, digital-cv, faq, index, link-in-bio, netlink-pay, pay5, plans, template, username-policy, verification, llms, manifest, robots, shared, sitemap. Inserts only, `on conflict do nothing`. No profile or landing page used any of them. Correction to the previous entry: the check is NOT browser-only, the database enforces it too.
- Open note: `reserved_usernames` grants TRUNCATE, REFERENCES and TRIGGER to `anon` and `authenticated`. Not reachable through the Supabase API, but worth revoking in a separate hardening change.
- **Reserved usernames: all app and public page names.** `RESERVED_USERNAMES` in `dashboard.html` and `page-builder.html` (both lists identical) now covers every `*.html` page name (including `ambassador`, `reward`, `checkout`, `admin`, `plans`, `card`, `analytics`, `faq`, `about`, `verification` and the rest) plus the technical paths `api`, `cv`, `page`, `assets`, `shared`, `sitemap`, `robots`, `manifest`, `llms`. No existing profile uses any of these names (checked in production). The check is still browser-only, a server-side check is a separate task. When a new `.html` page is added, add its name to both lists.
- **Ambassador: emails on approve and reject.** `admin-ambassador-update` now emails the applicant (their own auth email, via `getUserEmail`) when the status becomes `approved` ("Welcome to the Netlink Ambassador Program") or `rejected` ("Update on your Netlink Ambassador application", status "Not selected", no reason given). Under review and revoked send nothing on purpose (revoke is sent manually). Same sender and signature as the thank-you email (`SMTP_FROM_COMMUNITY`). A failed send never undoes the status change: the response has `email_sent` and the audit entry records `emailed`. The approved email promises no benefits. No migration, no new Vercel function. New `ambassadorStatusMail` in `api/_lib/mailer.js`.
- **Ambassador: thank-you email after submit.** After a successful application, `ambassador.html` calls `POST /api/orders?action=ambassador-thanks` (no new Vercel function). The server loads the caller's own `pilot-1` application, claims `thanks_emailed_at` atomically (only while `status = 'pending'` and the column is null, so one email per application), sends to the signed-in user's own auth email (never an address from the client) and releases the claim if the send fails. A failed email never affects the saved application. Signed by "Alex L Setiawan, Community & Growth Lead, Netlink". English copy, no promises, no em dash.
- `api/_lib/mailer.js`: `sendMail` accepts `from` and `replyTo`. `layout()` gains optional `after`, `signoff`, `footer`, `footerNote` (defaults unchanged, so finance emails render as before). New `ambassadorThanksMail`.
- **New Vercel env var (optional): `SMTP_FROM_COMMUNITY`**, for example `Netlink Community <community@netlink.bio>`. Community mail uses it and sets `Reply-To: community@netlink.bio`. Empty means it falls back to `SMTP_FROM` (finance). The SMTP login must be allowed to send as that address. Redeploy after adding it.
- Migration `supabase/migrations/20261004_ambassador_thanks_email.sql`: adds nullable `thanks_emailed_at` to `ambassador_applications`. Users cannot read or write it (column-level grants unchanged).
- **Ambassador Program, Pilot Season 1 (application only).** New in-app page `ambassador.html` (login required, `noindex`, listed in `robots.txt`, not linked from any navigation yet; open it by URL `/ambassador`). Logged-in members see a short explanation and an application form that is pre-filled from their profile (username, Net ID, referral code, country). The form asks for country and city, one of four tracks (Growth, Content, Community, Influence), 1 to 5 social media links, audience range, motivation, contribution plan and a terms checkbox. After submitting, the page shows the application status instead of the form.
- New table `ambassador_applications` (migration `supabase/migrations/20261004_ambassador_applications.sql`, applied to production 2026-10-04). One application per user per season (`unique (user_id, season)`). Status flow: `pending` -> `under_review` -> `approved` or `rejected`, and `approved` -> `revoked`, enforced by a trigger. RLS: users can only read and insert their own row; they cannot read `admin_notes`, and cannot update or delete. Reviews are done manually by an admin with the service role (no admin UI yet).
- No existing table was changed. No referral or reward logic is touched, so the program does not depend on the referral system.
- **Admin: Ambassadors tab.** `admin.html` has a new "Ambassadors" tab (visible to `super_admin` and `support`; the badge shows the number of pending applications). It lists applications with a status filter and username search, and opens a detail view with the applicant's account (email, Net ID, referral code, plan, identity status), their answers and links, and private admin notes. `super_admin` can save notes and move an application through the flow (pending -> under review -> approved or rejected, approved -> revoked) with a required note; `support` is read-only. Links shown in the detail view are only clickable when they start with `http://` or `https://`.
- New admin API actions in `api/_lib/admin.js` (served through `api/orders.js`, so no new Vercel function): `admin-ambassadors`, `admin-ambassador`, `admin-ambassador-update`. Roles are checked on the server on every call, status changes are atomic and follow the same flow as the database trigger, and every change is written to `admin_audit_log` (`ambassador_status`, `ambassador_notes`).
- Migration `supabase/migrations/20261004_ambassador_service_role_grants.sql` (applied to production 2026-10-04): grants `select, update` on `ambassador_applications` to `service_role`. The first migration did not include it, so the admin API could not read the table. Grants only, no data or policy change.

### Changed
- **Netlink Pay (`pay.html`, `pay2.html`, `pay5.html`): sharper card corners and shorter NET popup.** Card radius reduced by 30%: main card and swap card 24px to 17px, wallet bar, swap inner box and `.token-card` 20px to 14px, swap details card 16px to 11px, and the list/link cards (token list, ramp section on `pay2`/`pay5`, prepaid card link, transactions link) from Tailwind `rounded-2xl` (16px) to a new `.pay-card` class (11px). Modals, buttons, inputs and the deletion banner keep their radius. The "Why is NET excluded?" popup is shorter and now says NET is included automatically once a price is available.
- **Netlink Pay Total Balance card polish (`pay.html`, `pay2.html`, `pay5.html`).** Card is about 20% shorter (250px to 201px on a 390px phone, measured in headless Chromium): padding `p-6` to `p-5`, tighter gaps, and the logo box no longer forces a tall header row. The Netlink Pay logo moved up so its top lines up with the top of "Total Balance" (new `.pay-card-logo` class, negative margins). The `$` sign now has a thin space before the amount (`$ 1,234.56`). Only already-built Tailwind classes used, no rebuild needed.
- **Netlink Pay (`pay.html`, `pay2.html`, `pay5.html`): the main card is now "Total Balance" (USDC + POL), like most web3 wallets.** Before, the big number was the USDC balance only, so users with POL or NET read it as an empty wallet. The total is shown in USD (with the local currency line below, as before). NET is not counted because it has no market price yet (not listed on any CEX or DEX).
  - New label `Total balance excl. NET` with an info icon that opens a "Why is NET excluded?" popup. It replaces the NET ID text on the card (`cardIdDisplay` and `formatNetId` removed from these 3 pages; the NET ID stays on `identity.html` and the nav account sheet).
  - New eye icon to hide balances (total, per-token amounts and local values show `••••`). The choice is saved in `localStorage` (`netlinkPayBalanceHidden`).
  - Token list is now USDC, POL, NET. The USDC logo moved from the card to the USDC row, and USDC shows its local value there. Element IDs `balanceUsdc`, `balanceUsdcLocal`, `balancePol`, `balancePolLocal`, `balanceNet` are unchanged; new IDs are `balanceTotal` and `balanceTotalLocal`.
  - If the POL price cannot be loaded, the total shows `$--` instead of a partial number. Card color stays blue (a dark card was dropped because it loses contrast in dark theme). No Tailwind rebuild needed (new styles are inline in each page).
- **Netlink Pay test pages (`pay2.html`, `pay5.html`): added the Netlink Prepaid Card section.** Same markup as `pay.html` (coming soon, links to `card`), placed directly above Transaction History, below the ramp section. No new CSS classes, no Tailwind rebuild.
- **Netlink Pay test pages (`pay2.html` Onramp.Money, `pay5.html` Trails): Send, Receive and Buy buttons now use the same style as `pay.html`.** All three share the new `.wallet-action-btn` CSS (light theme: dark gray gradient, dark theme: USDC blue gradient, white text), so Buy is no longer green. Height stays 40px. Because these pages have three buttons, horizontal padding is 8px (16px in `pay.html`, which has two) so "Receive" stays on one line on narrow phones. The ramp sections, scripts and Buy behavior are unchanged. No Tailwind rebuild needed.
- **Netlink Pay (`pay.html`): Buy Crypto removed from production.** The "Buy Crypto" card (it only showed a "temporarily unavailable" placeholder) and the green "Buy" button are gone, so the wallet bar now has only Send and Receive. Removed the now unused `scrollToRamp()` function and the `#rampSection` CSS. The "Buy POL" link in the low-gas warning (send modal and the JS-built message) is now plain text: "You need POL for gas fees. Use Receive to deposit POL to your wallet." The on/off ramp keeps being tested in staging (`pay5.html`, unchanged). `pay2.html` untouched.
- **Netlink Pay: Send and Receive button style.** Same height as before (40px), same card padding, gap between buttons raised from 8px to 12px. Light theme: dark gray gradient with white text. Dark theme: the same blue gradient as the main USDC card. New `.wallet-action-btn` CSS lives in `pay.html` (no Tailwind rebuild needed, no new utility class).
- **Ambassador application form** (`ambassador.html`): removed the social media links field, since applicants already have a Netlink bio page. The review is now based on the bio page and the CV: on submit, `https://netlink.bio/<username>` is stored in the existing `social_links` column (no migration). Applicants without a username are asked to set one first. The status card shows links to the applicant's bio page and CV instead of the typed links.
- Added a required consent checkbox before the program terms: applicants agree that the Netlink team may review their bio page, their CV and the application, and confirm they have read the Privacy Policy. Both checkboxes must be ticked to submit (`terms_accepted_at` stores the time).
- **Admin Ambassadors tab**: the detail view now shows the applicant's bio page, CV page and the active links on the bio (read from the publicly readable `links` table by the admin page itself, so no database or permission change). A link typed in an older application is still shown as "Link in application". Links are clickable only when they start with `http://` or `https://`. `admin-ambassador` also returns `user_id`.
